# 작업 정리 표와 사용자 확인 안내 보완

## 1. 요청과 범위

T-WIN-004 후속입니다. 사용자는 작업 정리를 대상·담당, 확인된 결과, 남은 조건, 사용자 확인용 `.md`의 4열 표로 유지하고 긴 사용자 개입 안내를 표나 목록으로 정리하도록 지정했습니다. 기존 작업 ID·소유 상태·승인·보류·확인 완료 결과를 유지합니다.

담당 변경은 Windows work-rules의 [SKILL](../../../codex_windows/skills/work-rules/SKILL.md)과 [STYLE](../../../codex_windows/skills/work-rules/references/STYLE.md#작업-정리-표) 두 파일입니다. 다른 skill·개인 AGENTS·config·중앙 정책·소유 기능 문서는 변경하지 않았습니다.

## 2. 결과와 적용

| 대상·담당          | 확인된 결과                                                          | 남은 조건                                 | 사용자 확인용 `.md` |
|--------------------|----------------------------------------------------------------------|-------------------------------------------|---------------------|
| Windows work-rules | 4열 작업 정리 표, 실제 확인 문서 연결, 긴 개입 안내의 목록 구성 반영 | 독립 새 세션의 암묵 선택·장기 행동 미확인 | 사용자 확인 없음    |
| 지정 로컬 설치본   | 기존 차이 0개, 전체 44파일 전후 보존·반영·원본 해시 일치             | 다른 진행 중 채팅의 실제 적용 여부 미확인 | 사용자 확인 없음    |

현재 유효한 미해결 사용자 요청은 보고 맨 위에 모읍니다. 마지막 열은 사용자가 실제로 확인·시험·입력·선택을 진행할 `.md` 안내만 연결합니다. TODO·PLAN이나 단순 결과·참고 문서로 대신하지 않습니다. 준비된 실제 링크와 행동을 붙이고 확인 없음·agent 준비 중·보류를 구분하며 빈칸을 채우려고 새 문서나 없는 링크를 만들지 않습니다. 단순 질문과 한줄 알림에 표를 강제하지 않습니다.

후속 지정한 `@상황보고`의 [복사용 프롬프트](../../../codex_windows/skills/work-rules/references/STYLE.md#상황보고-호출문)를 같은 STYLE에 추가했습니다. 개인 보고 호출문이며 앱 명령·자동화 등록은 수행하지 않았습니다. `$work-rules`로 실제 제공 skill을 선택하고 호출 범위만 읽기 전용으로 보고합니다. 이 지시로 기존 승인 작업을 중단하거나 새 Goal·기능 실행·게시·다른 채팅 메시지를 시작하지 않습니다.

## 3. 검증과 한계

- 의미 검토: 최초 4열 규칙·후속 목록 변경·사용자 안내 열 정의와 호출문 보완의 필수 수정 각각 0건. 같은 입력 검토는 재사용했습니다.
- 공식 형식 검사: `quick_validate.py` 종료 0, `Skill is valid!`. 최초 의존성 부재 실패를 보존하고 기존 검증용 의존성을 자식 프로세스에서만 사용했습니다. 설치·전역 환경 변경은 없습니다.
- 문서 검사: 두 원본의 헤딩·파일 링크와 새 교차 앵커 통과. 표현 검사의 기존 진단 12건은 전후 같고 추가 0건입니다. 기존 푸터 부재·보존 예시 진단을 전체 통과로 표시하지 않습니다.
- 지정 설치: 원본·기존 설치본의 44파일 차이 0개를 확인했습니다. 전체 폴더·해시를 Git 제외 private에 보존한 뒤 work-rules 전체를 반영했고 44파일 일치를 확인했습니다.
- 공개 기록과 입력 해시는 [validation](validation.json)에 연결합니다. 원형 백업·실제 경로·검사 로그는 Git 제외 private에 보존합니다.

설치·내용 읽기와 독립 새 세션의 발견·암묵 선택·실제 행동은 구분합니다. 새 Goal·자동 메시지·상시 감시·게임/DB/실행 환경 변경은 수행하지 않았습니다. 게시 commit과 원격 SHA는 Git 기록·최종 보고에 연결합니다.

## 4. 복구와 이후 적용

이번 이전본과 현재 파일 해시를 먼저 대조하고 새 사용자 변경을 보존합니다. 복구가 요청되면 이번 두 파일 변경 범위만 검토하며 전체 폴더의 다른 차이를 임의 삭제하지 않습니다. 게시 후 복구는 검토한 revert로 진행합니다. 다음 실제 작업 정리에서 표·유효한 확인 문서·해결한 요청 제외를 관찰하며 별도 사용자 시험을 추가하지 않습니다.

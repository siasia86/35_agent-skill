# T-WIN-004 후속 모델 배정과 계획 담당 분리

2026-10-04 사용자가 승인한 구조 재검토·보완을 35 관리 원본에서 진행합니다. 기존 T-WIN-004와 [연속 실행 갱신](../2026-10-04-plan-continuation-T-WIN-004/README.md)의 후속이며 과거 검증·원문을 덮어쓰지 않습니다. [Windows PLAN](../windows/PLAN.md)의 후속 범위와 [TODO](../windows/TODO.md)의 새 세션 미확인을 연결합니다.

## 1. 담당과 변경 범위

- 구현 담당: 개인 [AGENTS](../../../codex_windows/AGENTS.md), [work-rules](../../../codex_windows/skills/work-rules/SKILL.md)와 [운영 상세](../../../codex_windows/skills/work-rules/references/operating-details.md), [planning-and-breakdown](../../../codex_windows/skills/planning-and-breakdown/SKILL.md)와 [동봉 대체 참조](../../../codex_windows/skills/work-rules/references/skills/planning-and-breakdown.md), Windows PLAN·TODO와 이 기록을 수정합니다.
- 통합 root: 이전 전체 원본/설치본·사용자 차이·해시·개인 설정 보존, 최종 검토·지정 설치·검증 기록·담당 staging·main 일반 게시를 담당합니다. 공통 파일은 root 한 곳에서 통합합니다.
- 기존 Kiro/Linux·역사 원문·다른 skill·system/plugin·개인 config·인증은 이번 구현에서 변경하지 않습니다. 새 skill을 추가하거나 fact-check의 사용자 설치 대기를 해제하지 않습니다.

## 2. 모델 배정과 업무 역할

명확한 지정 입력·추출 규칙·검증 방법이 있는 정형 작업은 Luna, 검색·비교·선별·출처 확인은 Sol 6.1 medium, 복수 조건 이미지 판정·여러 repo 계획과 의존성 분석은 Sol 6.1 high, 중요한 최종 설계 판단은 Astra를 사용자와 합의한 운영 기준으로 둡니다. 모델 성능 우열·정확도를 실측했다는 주장은 포함하지 않습니다. 작업별 도구의 실제 모델 ID·effort 지원과 선택을 확인하며 기본 main/config는 자동 변경하지 않습니다. 짧은 조회와 지원하지 않는 분담은 root가 직접 수행합니다.

사용자의 단일 창구인 orchestration root가 필요한 역할만 배정하고 최종 배정·검증·공통 파일 통합을 담당합니다. 큰 계획의 planner는 CPO 요구·우선순위·완료 기준과 CTO 기술·의존성·검증·복구 관점을 묶어 초안을 작성합니다. COO는 필요할 때 배정·진행 정리안을 지원하고 CISO는 보안 영향 변경에서 관련 범위만 검토합니다. 기능 원본·실제 상태는 소유 담당에게 유지합니다. 단순 작업은 직접 수행하고 입력·범위·승인이 같은 검토는 재사용합니다.

역할 명칭만으로 새 권한·직책별 필수 승인·자동 채팅/메시지·Goal·상시 감시를 생성하지 않습니다. 계획만 요청되면 구현·게시를 시작하지 않습니다. repo 역할·범위 문서가 있으면 참조하되 공통 개인 skill에 특정 repo 경로를 강제하지 않습니다.

## 3. 반환 근거와 실패 처리

반환에는 출처·조사 범위·실제 개수·누락·오류·미확인을 남깁니다. 오류 발견 시 증거를 보존하고 입력·도구·판단 오류를 구분하여 영향받은 결과의 사용을 보류합니다. 원인을 교정하거나 적합한 모델/root에 인계한 뒤 해당 범위만 재검증합니다. 같은 실패를 새 근거 없이 반복하거나 기존 결과 전체를 무조건 재검증하지 않습니다.

## 4. 검증과 적용 관찰

구현·정적 검증·설치·게시·새 세션 발견·선택·실제 분담 행동을 각각 실제 관찰로 기록합니다. 구조 검사는 공식 skill-creator quick_validate, 문서는 실제 동봉 검사기와 현재 대상의 설정·제외 범위, 변경은 git diff 검사를 사용합니다. 개인 설정·raw는 Git 제외 private에 보존하며 공개 기록은 상대 경로와 비식별 집계만 담습니다.

구현 담당의 검증: 네이티브 Python 3.14.8로 공식 quick_validate의 두 skill 구조 검사를 통과했습니다. 전역 PyYAML 부재를 확인한 뒤 기존 업데이트의 격리된 검증 의존성을 재사용했으며 패키지를 새로 설치하지 않았습니다. 변경 Markdown 8개·파일 링크 55개·헤딩 77개에서 링크/헤딩 이슈는 0건입니다. 문서 표현은 개인 지침/skill 5개에 기존 푸터 비강제 기준의 `--no-footer`, 관리 기록 3개에 기본 검사를 적용하여 이슈 0건을 확인했습니다. 초기 검사의 새 표 정렬 진단 15건은 표만 정렬하여 해결했고, 푸터 진단 15건은 기존 개인 지침/skill의 미채택 범위와 구분했습니다. git diff --check도 통과했습니다.

원본 보존 대조: work-rules 44개 파일 중 지정 3개, planning-and-breakdown 9개 파일 중 본문 1개만 변경했고 skill 내부 파일 추가·삭제는 0개입니다. direct/fallback planning의 COMPAT 밖 역사 원문 bytes를 각각 보존했고 두 활성 지침은 기존 상대 링크 2개를 제외하면 동일합니다. 검증한 담당 변경만 root에 인계합니다.

통합 root가 원본·설치본 차이 0건을 확인하고 이전 전체 사본·해시를 private/before에 보존한 뒤 두 skill 53파일을 지정 설치했습니다. [설치 결과](installation.json)와 before/after inventory에서 목록·bytes·SHA-256 일치, 개인 AGENTS의 로컬 추가 본문·config·다른 개인 skill 여섯 폴더 보존을 확인했습니다. Luna의 effort는 낮은 값 우선 대신 실제 지원 기본값에서 필요한 경우 조정하도록 보완했습니다. 최종 게시 결과는 실제 원격 확인 뒤 기록합니다. 새 세션의 암시적 발견·선택·업무 행동과 모델 성능 실측은 현재 미확인입니다. 정적 검사나 설치 해시 일치를 그 성공으로 처리하지 않습니다.

## 5. 복구와 보존

통합 후 설치 지침과 02 역할 문서로 네 가지 요청의 처리 경로를 독립 검토했습니다. 검토만 요청하면 수정·게시를 시작하지 않고, 공유 파일 충돌은 해당 구간만 대기하며, 모델 도구가 없으면 한계를 밝히고 직접 처리하고, 사용자 보류 Goal은 추출 요청으로 재개하지 않는 경로를 확인했습니다. 실제 입력을 실행한 행동 시험·자동 발견·모델 정확도 측정은 수행하지 않았습니다. 최종 서식 보완 뒤 두 설치 폴더 53파일을 다시 원본과 맞추고 개인 AGENTS 추가 본문·config·다른 여섯 폴더의 보존을 재확인했습니다. 실제 게시 SHA는 통합 작업의 결과 기록과 최종 보고에서 확인합니다.

복구 전에 현재 원본/설치본과 이번 after 해시를 대조하여 이후 사용자 변경을 식별합니다. 이번 private/before의 지정 전체 skill 폴더와 개인 AGENTS를 선택 복원하거나 현재 차이와 병합합니다. 변경하지 않은 config·다른 skill을 일괄 덮어쓰지 않습니다. 게시 이후 복구는 검토한 revert를 사용하며 기존 역사 원문과 다른 작업 변경을 보존합니다. 다운로드·설치·발견·선택·행동·게시 상태와 기존 fact-check 설치 대기는 별도로 유지합니다.

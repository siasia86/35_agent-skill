
# 장애 복구

## 장애 처리

추가 변경 중단 → 로그·상태 보존 → 장애 확인·원인 진단 → 원인 수정 → 재발 방지 → 검증 후 재개의 순서로 진행합니다. 영향받는 작업을 멈추되 관계없는 승인 작업까지 무조건 중단하지 않습니다. 읽기 전용 진단 요청은 재시작·배포·데이터 복구를 허용하지 않습니다.

1. 증상과 발생 시간·대상을 확인하고 안전한 최소 재현을 만듭니다. 정상 상태와 비교할 로그·지표·최근 코드/구성/배포 변경을 필요한 범위에서 보존합니다.
2. 네트워크·프로세스·저장장치·권한/인증·구성·배포·외부 서비스 중 실패 계층을 좁힙니다. 가설마다 반증 가능한 증거를 선택하고 실제 관찰과 가설을 구분합니다.
3. 관련 없는 변수와 최근 변경을 줄여 원인을 재현합니다. 로컬 health 결과를 다른 대상의 건강 증거로 쓰지 않습니다.
4. 재시작만 반복하는 대신 원인을 수정합니다. 예를 들어 메모리 누수·한도, 디스크 부족·로그 회전, 실제 접근 규칙을 조사합니다. 운영 변경은 승인된 대상과 복구 조건에서만 수행합니다.
5. 실제 요청 범위에 필요한 회귀 검사·모니터링·운영 절차를 보완합니다. 새로운 자동 복구나 상시 감시를 임의로 만들지 않습니다.
6. 장애를 재현한 경로와 정상 동작·지표 회복·정합성을 검사합니다. 원인을 확인하지 못했다면 복구 가설과 남은 증거를 보고합니다.

서비스·이벤트·HTTP 조사와 도구별 실패 분류는 [Windows 진단](../windows/diagnostics.md)을 읽습니다.

## 복구 판단

배포 직후라는 시간만으로 모든 대상에 일괄 rollback하지 않습니다. 서비스 영향·데이터 손실·구버전 호환성·검증된 복원 수단을 확인해 이전 버전 복귀, 제한된 기능 비활성화 또는 전진 수정을 선택합니다. 데이터 마이그레이션 포함만으로 rollback 불가라고 단정하지 않습니다.

인프라 state는 실제 리소스·데이터 백업이 아닙니다. 이전 state 덮어쓰기를 리소스 rollback으로 사용하지 않습니다. state 손상은 snapshot·lineage·serial·실제 소유 상태를 따로 확인하고 force-unlock·import·교체를 오류 메시지만 보고 실행하지 않습니다.

각 복구 변경을 작게 나누어 영향과 되돌릴 방법을 먼저 정하고 적용 후 검증합니다. 최종 보고에는 원인, 수정, 정상화 증거, 재발 방지, 남은 문제와 미실행 항목을 포함합니다.
## 실행 기준

현재 사용자 요청·적용 저장소 지침·플랫폼 정책과 실제 권한을 따릅니다. 저장소 작업은 실제 Git 루트·기존 변경·하위 지침부터 확인하고 다른 작업과 비공개 자료를 보존합니다. 검토·명세 작성은 설치·운영 적용·게시 권한을 추가하지 않으며 이미 승인된 범위는 반복 확인하지 않습니다.

Windows PowerShell을 사용하고 파일 작업은 확인한 절대 경로와 `-LiteralPath`로 처리합니다. Python이 필요한 경우 실제 Python 3.11 이상을 확인해 `python -X utf8 -B`로 호출하고 UTF-8 입출력을 명시합니다. PowerShell 오류와 외부 명령의 `$LASTEXITCODE`를 각각 판정합니다. 업무에 필요한 선택 도구만 실제 설치·대상·권한을 확인하며 자동 설치하지 않습니다. Windows 네이티브에서 실행할 수 없는 기능은 범위 밖으로 표시합니다.

한국어로 결과와 실제 근거를 보고하고 통과·부분 검사·실패·미실행을 구분합니다. 폴더 안의 해당 참조만 필요할 때 읽으며 다른 저장소·형제 스킬 설치를 필수로 요구하지 않습니다.
